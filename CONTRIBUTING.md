## iOS Testers & Contributors Wanted

**We are actively looking for iOS developers and testers to help validate and improve the iOS implementation.**

The iOS layer is architecturally the most involved part of this library. It uses a UIKit → SwiftUI bridge (`UIHostingController`), a custom `CAFilter variableBlur` path for progressive blur, and a `UIViewPropertyAnimator` technique for correct custom blur intensity — none of which are straightforward to test without a real Mac + Xcode environment. `LiquidGlassView` on iOS is newer still (currently a blur + frosted-highlight approximation — see [Architecture](#architecture)) and needs coverage too.

If you have access to a macOS machine with Xcode 16.1+ and can test on a physical iOS device or simulator, your contributions are especially valuable. Areas where help is most needed:

- **Regression testing** — verifying blur rendering across iOS 16, 17, and 18
- **Progressive blur** — validating `ProgressiveBlurView.swift` on different device sizes and orientations
- **`LiquidGlassView` fallback** — validating the frosted-highlight approximation looks right across device sizes, and helping scope what a real iOS refraction path (Metal / SwiftUI `Shader` on iOS 17+) would need
- **Accessibility** — confirming the Reduce Transparency fallback works correctly across OS versions
- **SwiftUI interop** — catching edge cases in `BlurVibeSwiftUIView.swift` when used inside SwiftUI-hosted RN screens
- **Performance profiling** — identifying overdraw or frame drops in blur-heavy UIs

To get involved, open an issue tagged `ios` or `help wanted`, or comment on an existing one. You are also welcome to open a PR directly — even a partial fix or a test result posted as a comment is a meaningful contribution.

## Getting Started

### Prerequisites

Make sure you have the following installed:

- **Node.js** >= 18.0.0
- **Yarn** 4.x (this project uses Yarn workspaces with Yarn Berry)
- **Android Studio** with Android SDK (for Android development)
- **Xcode** >= 16.1 (for iOS development, macOS only)
- **CocoaPods** (for iOS development)
- **Ruby / Bundler** (the example app uses a `Gemfile` to pin the CocoaPods version)

Android's native blur engine (C/NDK) is built automatically via the
Android Gradle Plugin's `externalNativeBuild` — no separate NDK install
or configuration step is needed beyond a standard Android Studio setup.

### Setup

```sh
# 1. Fork the repo on GitHub, then clone your fork
git clone https://github.com/I-am-Pritam-20/react-native-blur-vibe.git
cd react-native-blur-vibe

# 2. Install dependencies
yarn install

# 3. Install iOS pods (macOS only)
cd example/ios && bundle exec pod install && cd ../..
```

> **Note:** This project uses Yarn Berry (4.x) with the release committed to `.yarn/releases/`. You do not need to install Yarn globally — just run `yarn` and the pinned version will be used automatically.

## Project Layout

`src/` holds the TypeScript you'll actually edit — the public components (`BlurView.tsx`, `LiquidGlassView.tsx`), their prop types, and the codegen native-component specs used for New Architecture. `lib/` is compiled output; never edit it directly, it's regenerated by `yarn prepare`.

`ios/` is Swift plus a thin Objective-C bridge layer, split into a `Views/` subfolder for the visual composition (blur, progressive blur, overlay, noise, and the liquid-glass fallback) and top-level files that host those views for React Native and expose props across the bridge, for both Old and New Architecture.

`android/` is Kotlin, plus a small `src/main/cpp/` folder holding the native (C/NDK) blur engine used on older Android versions, and `src/main/res/raw/` holding the AGSL shader source used for real-time refraction on newer ones. The `*ViewManager.kt` files are the React Native bridge layer, dispatching props to whichever internal implementation is active for the running API level.

`example/` is a full RN app used for manual, on-device testing — it's pre-linked to the local library, so changes in `src/`, `ios/`, or `android/` show up there without republishing anything.

`.github/workflows/` contains the CI pipelines described under [Testing](#testing) below.

## Architecture

### Two components, two techniques

- **`BlurView`** — pixel averaging (backdrop blur). Works everywhere (iOS 13+, Android 21+).
- **`LiquidGlassView`** — real-time optical refraction ("liquid glass") where a real shader path exists, blur + a static frosted highlight elsewhere. These are genuinely different rendering techniques (geometric light-bending vs. pixel averaging), which is why they're separate components rather than one component with a mode flag.

| Platform | `LiquidGlassView` technique |
|---|---|
| Android API 33+ | Real refraction via `RuntimeShader` (AGSL) |
| Android API < 33 | Blur + static diagonal highlight + rim stroke (approximation) |
| iOS (all versions currently) | Blur + static diagonal highlight + rim stroke (approximation) — a real Metal/SwiftUI-`Shader`-based refraction path for iOS 17+ is a planned future direction; see [iOS Testers & Contributors Wanted](#ios-testers--contributors-wanted) |

### Android: three implementation tiers, gated by API level

| API level | Class | Technique |
|---|---|---|
| 21–30 | `BlurVibeView` + `LegacyBlurController` | Native C blur engine (primary), RenderScript (fallback), software `BlurMaskFilter` (last resort) |
| 31–32 | `BlurVibeViewApi31` | GPU `RenderEffect` |
| 33+ (`LiquidGlassView` only) | `LiquidGlassShaderView` | `RuntimeShader` (AGSL) |

Each `*ViewManager` picks the right class in `createViewInstance()` based on `Build.VERSION.SDK_INT`. If you're adding a prop, it needs a handler in the `ViewManager` that dispatches to whichever class is active — see any existing prop (e.g. `blurAmount`) for the pattern.

### Shared capture: `BlurCaptureCoordinator` (Android)

The expensive part of backdrop blur is capturing what's behind the view. **This is shared once per screen root**, not once per `BlurView`/`LiquidGlassView` instance — see the class doc in `BlurCaptureCoordinator.kt` for the full rationale. If you're adding a new component that needs backdrop content, register with the existing coordinator (`BlurCaptureCoordinator.forRoot(root)`) rather than adding a new independent capture path. Two prior implementations of independent per-view capture were tried during this project's development and both caused real performance problems with multiple views on screen — don't reintroduce that pattern.

### Self-exclusion: `BlurVibeCanvas` (Android)

When the coordinator captures the root, every participating view must skip drawing itself (otherwise it captures its own previous output — a feedback loop, not a crash, but visibly wrong). This is done via a marker `Canvas` subtype, checked in every view's `draw()`:

```kotlin
override fun draw(canvas: Canvas) {
  if (canvas is BlurVibeCanvas) return
  super.draw(canvas)
}
```

A boolean flag was tried first and doesn't generalize correctly to multiple simultaneously-registered, possibly-overlapping views — the canvas-type check does, since it doesn't depend on any per-instance state. If you add a new view class that participates in capture, it needs this exact check.

## Safety Rules for Native / GPU Code

These aren't style preferences. Each one exists because the alternative caused a confirmed crash or correctness bug during this project's development.

### 1. Never persist a `RenderNode` across frames (Android)

```kotlin
// DON'T — this raced with RenderThread and caused a confirmed SIGSEGV
// when Reanimated was in the component tree.
private val node = RenderNode("MyNode")   // one instance, reused every frame
override fun onDraw(canvas: Canvas) {
  node.beginRecording()   // races with RenderThread replaying a QUEUED
  ...                      // reference to this SAME object from the
  node.endRecording()      // previous frame
  canvas.drawRenderNode(node)
}

// DO — a fresh object every single onDraw() call. RenderThread only ever
// replays a fully-recorded, immutable, frame-specific object; the main
// thread's next recording always targets a different one.
override fun onDraw(canvas: Canvas) {
  val node = RenderNode("MyFrame")
  node.beginRecording()
  ...
  node.endRecording()
  canvas.drawRenderNode(node)
}
```

`BlurVibeViewApi31` and `LiquidGlassShaderView` both follow this discipline. Reanimated can trigger an independent `invalidate()`/redraw cycle for a different frame while your capture+record is in flight — the only way this is safe is a fresh object every frame.

### 2. Kotlin method names must not collide with supertypes (Android)

`View`, `ReactViewGroup`, and `BaseViewManager` all declare methods that are easy to accidentally re-declare with the same name/signature, which Kotlin then requires `override` for. Known collisions in this codebase:

| Supertype method | Use instead for your own logic |
|---|---|
| `View.setEnabled(Boolean)` | `applyBlurEnabled` |
| `ReactViewGroup.setBorderRadius(Float)` (final, can't even override) | `applyBorderRadius` |
| `BaseViewManager.setBorderRadius` | `setBlurBorderRadius` (on the ViewManager) |

If the compiler says "hides member of supertype" or "is final and cannot be overridden," rename — don't fight the supertype.

### 3. Native C: prefer verifiable techniques over reproducing constants from memory (Android)

If you're touching `blur_engine.c`: any change here can produce a segfault, which — unlike a Kotlin/Swift exception — cannot be caught or gracefully degraded from.

- Every buffer allocation must be null-checked, and every return path must free exactly what was allocated and unlock the bitmap if and only if it was successfully locked. Trace every return path by hand before submitting.
- Use `info.stride`, never assume `width * 4` — some devices pad rows.
- If you're adding a lookup table of precomputed constants, transcribe directly from a real, verified source — never from memory/recollection. A wrong constant produces silently incorrect pixel output with no way to detect it.
- This engine is only ever loaded on API < 31 — `BlurVibeViewApi31` and `LiquidGlassShaderView` (API 31+) never touch it. Keep it that way.

### 4. Multi-threaded native calls: only ever touch disjoint memory ranges (Android)

`BlurThreadPool` splits each blur pass across several threads, each calling into `blur_engine.c` with a different `threadIndex`. Each call only reads/writes its own row or column slice of the bitmap — never overlapping ranges. If you change the slicing math, verify by hand that every row/column is covered exactly once across all threads, with no gaps and no overlaps, for non-evenly-divisible sizes too.

## Development Workflow

### Running the example app

The `example/` app is pre-linked to the local library via `react-native.config.js`. Any changes you make in `src/`, `ios/`, or `android/` are immediately reflected after the steps below.

```sh
# Build the TypeScript source first (always do this before running the app)
yarn prepare

# Run on Android
yarn example android

# Run on iOS (macOS only)
yarn example ios
```

### Rebuilding after TypeScript changes

```sh
yarn prepare
```

This compiles `src/` into `lib/` (CJS, ESM, and type declarations). Run this whenever you change TypeScript files.

### Rebuilding after native changes

**Android** — the example app rebuilds native code automatically when you run `yarn example android`, including the C blur engine if you touched `android/src/main/cpp/`.

**iOS** — if you changed the podspec or added new files, re-run pod install first:

```sh
cd example/ios && bundle exec pod install && cd ../..
yarn example ios
```

For Swift-only changes (no new files, no podspec change), a regular `yarn example ios` build is sufficient.

## Making Changes

### TypeScript / React

- Edit files in `src/`
- Run `yarn prepare` to rebuild
- Run `yarn typecheck` to verify types
- Run `yarn lint` to check code style

### iOS (Swift)

The iOS implementation is split across two layers:

- **`ios/Views/`** — the visual layer. `BlurVibeSwiftUIView.swift` composes blur, progressive blur, overlay tint, and noise for `BlurView`. `BlurEffectView.swift` handles `UIVisualEffectView` intensity via `UIViewPropertyAnimator`. `ProgressiveBlurView.swift` implements variable-radius blur using a private `CAFilter`. The `LiquidGlassView` fallback composition reuses this same blur layer plus a highlight/rim overlay — see [Architecture](#architecture).
- **`ios/BlurVibeView.swift`** (and its `LiquidGlassView` counterpart) — the UIKit host. Bridges the SwiftUI view into the RN view hierarchy via `UIHostingController`.
- **`*ViewManager.swift` + `.m`** (Old Architecture) and **`*ViewFabric.mm`** (New Architecture) — the React Native bridge. Exposes props to JS on both architectures.

Test via `yarn example ios` on macOS. See [iOS Testers & Contributors Wanted](#ios-testers--contributors-wanted) if you want to help with iOS coverage — `LiquidGlassView`'s fallback path especially needs more real-device testing.

### Android (Kotlin)

Read [Architecture](#architecture) and [Safety Rules](#safety-rules-for-native--gpu-code) above before making non-trivial changes here — both sections exist specifically to prevent regressing bugs that were previously fixed. In short: three API-level tiers per component, one shared capture coordinator per screen, fresh `RenderNode`s every frame, and careful native buffer/lock lifecycle management in the C blur engine.

Test via `yarn example android`.

## Testing

### Automated (GitHub Actions)

Every push and pull request automatically runs:

- **Lint** — ESLint checks (`ci.yml`)
- **Typecheck** — TypeScript compilation (`ci.yml`)
- **Android build** — full Gradle debug build, including the native C blur engine, on `ubuntu-latest` (`build-android.yml`)
- **iOS build** — full Xcode build on `macos-15` (`build-ios.yml`)

You do not need to run these locally — push your branch and check the **Actions** tab on GitHub.

### Manual testing checklist

When submitting a PR that touches native code, please test and confirm the following if you have the environment available:

**Android:**
- [ ] `BlurView` renders correctly on API 31+ device/emulator (`RenderEffect` path)
- [ ] `BlurView` renders correctly on an API 21–30 emulator (native C blur engine path)
- [ ] `LiquidGlassView` shows real refraction on an API 33+ device/emulator
- [ ] `LiquidGlassView` shows the blur+highlight fallback correctly on API < 33
- [ ] Multiple `BlurView`/`LiquidGlassView` instances on one screen at once (e.g. inside a `FlatList`) stay smooth
- [ ] Overlapping/stacked blur views (e.g. a card inside a modal) render correctly, not as a feedback-loop smear
- [ ] With `react-native-reanimated` present and actively animating something near a blur/liquid-glass view — no crash
- [ ] `overlayColor` with alpha shows a tint over the blur
- [ ] `overlayColor: "#00000000"` shows pure blur with no tint
- [ ] Children render on top of the blur layer
- [ ] `progressiveBlurDirection` variants work on API 31+
- [ ] Split-screen / multi-window mode still updates blur correctly, if you touched `BlurCaptureCoordinator`

**iOS:**
- [ ] `BlurView` renders correctly on device and simulator
- [ ] `blurType` variants all work (`light`, `dark`, `systemMaterial`, etc.)
- [ ] `blurAmount` produces a visible intensity difference
- [ ] `overlayColor` with alpha shows a tint over the blur
- [ ] `progressiveBlurDirection` variants render the correct gradient mask
- [ ] `LiquidGlassView`'s blur+highlight fallback renders correctly
- [ ] Reduce Transparency accessibility setting triggers the fallback color
- [ ] Children render on top of the blur layer

If you don't have access to both platforms, note in your PR which platforms you tested on. Other contributors or maintainers will cover the rest — partial testing is still a meaningful contribution.

## Submitting a Pull Request

1. **Fork** the repo and create a branch from `main`:
   ```sh
   git checkout -b fix/android-blur-api-28
   ```

2. **Make your changes** following the guidelines above.

3. **Run checks locally:**
   ```sh
   yarn lint
   yarn typecheck
   yarn prepare
   ```

4. **Commit** using the convention below.

5. **Push** to your fork:
   ```sh
   git push origin fix/android-blur-api-28
   ```

6. **Open a Pull Request** against `main` on this repo.

7. **Fill in the PR template** — describe what changed and why, and note which platforms you tested on. If your change touches anything under [Safety Rules](#safety-rules-for-native--gpu-code), explain specifically how you verified it (e.g. "traced every return path in blur_engine.c by hand," "tested with Reanimated present on a physical device").

8. **Wait for CI** — all workflow checks must pass before merge.

9. **Address review feedback** if any.

## Reporting Bugs

Open an issue using the **Bug Report** template (`.github/ISSUE_TEMPLATE/bug_report.yml`). Please include:

- React Native version
- Platform (iOS / Android) and OS version
- Device or emulator details
- Minimal reproducible code
- What you expected vs. what happened
- Logs or screenshots if available

The more detail you provide, the faster it gets resolved.

## Commit Convention

This project uses [Conventional Commits](https://www.conventionalcommits.org/):

```
feat:      new feature
fix:       bug fix
docs:      documentation only
style:     formatting, no logic change
refactor:  code change that is neither a fix nor a feature
perf:      performance improvement
test:      adding or fixing tests
chore:     build process, tooling, dependencies
```

Examples:

```sh
git commit -m "feat: add vibrancy support for iOS"
git commit -m "fix: android blur not updating on layout change"
git commit -m "docs: update project structure in CONTRIBUTING"
git commit -m "chore: bump react-native peer dep to 0.76"
```
